# 推甄口頭講稿重點

給自己看的講稿大綱，不是投影片。目的是把整場專案做下來的東西，整理成幾個能被追問也答得出來的重點。細節與數字出處都在 [`docs/progress_log.md`](progress_log.md)，這裡只放結論跟怎麼講。

---

## 1. 三分鐘專案介紹

> 這個專案叫「AI Network Intrusion Detection」，目標是輸入網路流量，讓模型判斷三件事：這筆流量是正常還是攻擊、如果是攻擊屬於哪一種類型、以及模型對這次判斷有多少信心。
>
> 我用的是官方 CIC-IDS2017 真實資料集，五個工作日、8 個原始檔案，合計 310 萬筆流量、80 個特徵。我沒有直接套用資料集就開始訓練，而是先花時間做完整的資料探索（EDA），發現資料本身有品質問題（重複列、整批空白列、無限值），確認清理策略之後才開始建模。
>
> 模型的部分，我先建立一個 Logistic Regression 當基準，再換成 Random Forest，隨機切分測出來準確率 99.96%。但這個專案真正做的事情，不是停在這個高分，而是**反覆質疑這個高分可不可信**——換了三種不同的切分方式重新驗證，發現分數在不同情境下差異非常大，也因此抓到兩個真正的工程問題。最後把模型包成一個 API 跟一個離線重播儀表板，可以實際輸入流量看到「攻擊與否／攻擊類型／信心分數」三個結果同時輸出。

## 2. 為什麼不能只看 Accuracy

準備好一次講完這四層,被追問哪一層都能往下展開:

1. **類別不平衡**：`BENIGN` 佔約 73%，一個什麼都不學、永遠猜「正常」的偷懶模型，準確率就有 80.3%。所以任何模型的準確率，都要先跟這個「偷懶基準線」比較才有意義。
2. **準確率看不出錯在哪裡**：混淆矩陣才看得出來是「誤報」（正常被當攻擊）還是「漏報」（攻擊被當正常）。對入侵偵測系統來說，漏報是遠比誤報危險的錯誤類型。
3. **切分方式會嚴重影響分數，而且會被隨機切分掩蓋**：同一個 Random Forest，隨機切分測出 Recall 99.86%；但改成「星期一至四訓練、星期五測試」，Recall 直接掉到 **7.93%**。隨機切分會把高度相似的流量同時分進訓練集跟測試集，讓模型表現被高估。
4. **「信心高」不等於「校準」**：我一開始只驗證「猜錯時信心會不會下降」，這只證明信心分數有一定的區分能力，不是校準。後來正式算 ECE（Expected Calibration Error），才發現隨機切分的模型是真的校準良好（ECE 0.05%），但跨日期測試的模型 ECE 高達 **32.97%**——它有 88% 的預測都宣稱 99.7% 有信心，這批預測實際只答對 66.8%。也就是說，換到新的資料分布之後，模型不只是變差，連「自己在瞎猜」都不知道。

## 3. 過程中真正抓到、修掉的兩個問題

不是講「我做了很多實驗」，是講「我抓到了會讓結論失真的具體錯誤」：

**問題一：`source_file` 洩漏進模型特徵**
在做按日期切分驗證時，第一版程式不小心把 `source_file`（這筆資料來自星期幾的哪個檔案）當成一般欄位做了 one-hot encoding，等於把「今天星期幾」直接餵給模型當特徵。如果沒抓到，模型很可能不是在學攻擊模式，是在背檔名，測出來的分數會失去意義。訓練前發現、修正，並加了迴歸測試防止再發生。

**問題二：API 展示資料被重複標準化**
把模型包成 API 給網頁展示時，範例資料是直接從已經標準化過的 `processed/test.csv` 裡抓的，但 API 的 `/predict` 又對這批資料做了一次標準化，等於重複處理，模型看到的是失真的雜訊。我當時在瀏覽器上測出「一筆 `DoS GoldenEye` 流量被誤判成 `BENIGN`（93% 信心）」，一開始還把這個寫進正式紀錄，說是「模型既有的誤判、刻意保留」——這個結論後來被證實是錯的，因為那筆資料本身就是被弄壞的，不能代表模型真正的行為。後來修正成用 `inverse_transform` 還原成原始尺度，並加了測試讓 API 的預測結果，必須跟「前處理只做一次」的正確流程一致，否則測試會失敗。

**這兩個問題共同的教訓**：一個「看起來合理」的結果，不代表流程本身沒問題；需要回頭查證資料在每一個環節有沒有被正確處理。

## 4. 模型目前做不到什麼（誠實列出限制）

1. **無法可靠泛化到新的一天／新的攻擊模式**：星期一至四訓練、星期五測試，Recall 從 99.86% 掉到 7.93%；`Bot`、`PortScan` 幾乎完全偵測不到。但這個測試同時包含「日期變了」跟「攻擊類型從沒見過」兩種效應，不能把整個分數下滑都歸因於資料洩漏。
2. **就算類別都看過，行為隨時間變化時模型也跟不上**：用「每個攻擊類型各自依時間排序、切出最新 20% 當測試」（`temporal-per-class`，是分層的類別內時間切分，不是全資料共用同一時間點的部署型驗證）驗證，`DoS Slowhttptest` 的 Recall 從 99.07% 掉到 26.64%，`Web Attack XSS` 從 56.67% 掉到 0.77%——這些類別在訓練集裡都出現過，代表問題不是「沒看過」，是「這個類別的攻擊行為本身有時間漂移」。
3. **極少數類別的評估數字不穩定**：`Web Attack Sql Injection` 測試集只有 4 筆，錯 2 筆就是 50%，這種樣本數下的百分比沒有統計意義，只能當參考。
4. **可能有一定程度依賴 port 資訊**：Permutation importance 顯示 `destination_port` 邊際重要性很高；但整組拿掉重新訓練後，Recall 只掉不到 1 個百分點、Precision 明顯下降——結論是 port 主要幫助降低誤報，不是攻擊偵測能力的唯一依據，但仍是需要留意的潛在捷徑。
5. **儀表板是離線重播，不是正式監控**：展示用的 97 筆是刻意平衡過的樣本（每個類別各自取幾筆正確／錯誤案例），畫面上的攻擊比例、漏報比例不能解讀成真實網路環境裡的實際發生率。

## 5. 如果做下一版，會怎麼改善跨日期泛化

1. **把「跨時間切分」當成預設評估方式，不是事後才驗證的加分項**：一開始就用時間或日期切分當標準評估流程，而不是先用隨機切分拿到好看的數字，才回頭檢查可不可信。
2. **用涵蓋更長時間、更多次攻擊活動的資料訓練**：現在只有一週的擷取資料，同一種攻擊工具只出現一次設定；如果能拿到跨越多週、多次攻擊活動的資料，模型才有機會學到「攻擊的通用行為模式」而不是「這次擷取剛好長怎樣」。
3. **減少對特定基礎設施痕跡的依賴**：像 port 號碼這種容易受這次擷取環境影響的特徵，可以做敏感度分析、必要時降低權重，讓模型更依賴封包時間分布、流量統計比例這類比較通用的行為特徵。
4. **針對極少數類別，先補資料再談重取樣技巧**：`Bot`、SQL Injection 這種類別的根本問題是資料太少，SMOTE 這類合成取樣不一定能解決，優先順序應該是想辦法取得更多真實樣本。
5. **考慮加入非監督式的異常偵測作為輔助**：監督式分類天生無法辨識「訓練時完全沒看過的攻擊類型」；如果能搭配異常偵測（找出「不像任何已知類別」的流量），至少能對全新的攻擊手法發出警示，而不是直接被歸類成正常。
